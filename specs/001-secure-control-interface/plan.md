# Plan: Secure, multi-transport control interface

**Spec:** ./spec.md
**Status:** Ready for tasks

## Approach

Put a single authorisation gate in front of the command path that already
exists, then add two independent links that both pass through it. Every command
— BLE or HTTP — is verified by one `auth` component and dispatched by the
untouched `controller_handle()`. This is the payoff for the earlier refactor:
adding two transports changes no actuator, positioner or command code.

Authorisation is an **HMAC-SHA256 signature plus a monotonic nonce**, not TLS.
TLS was ruled out deliberately: mbedTLS costs flash we do not have, handshakes
are slow on the S3, and a self-signed certificate is rejected by browsers
anyway — so it would be the most expensive option that still fails the one case
it was meant to fix. Signing gives authenticity and replay protection for a few
kilobytes, and the app is the only client that must work.

BLE carries pairing, provisioning and short-range control. Wi-Fi runs **APSTA**:
it joins the operator's hotspot when credentials exist, and always keeps its own
access point up as fallback so the dock can never become unreachable.

Work is sequenced so each phase ends in something demonstrable, because the
combined BLE + Wi-Fi scope is the largest of the options considered and may not
finish inside the semester. If it stops after Phase 2 you still have a secure,
hotspot-capable dock.

## Architecture / components

```
BLE (NimBLE GATT) ─┐
                   ├─► auth_verify() ─► controller_handle() ─► actuator / positioner
HTTP (signed)    ──┘        │                  (unchanged)
                            └─► session_touch()  ─► dead-man watchdog
```

| Component | Hardware-free | Responsibility |
| --- | --- | --- |
| `auth/` | **yes** | Canonical request string, nonce ordering, constant-time compare. Host unit tested. The HMAC primitive is injected so the host build needs no mbedTLS. |
| `secrets/` | no | NVS: device key, nonce high-water mark, Wi-Fi credentials |
| `session/` | partly | Per-transport dead-man timers; generalises the webserver's current heartbeat |
| `wifi_link/` | no | APSTA, station join with fallback, mDNS `dock.local` |
| `ble_link/` | no | NimBLE GATT: pairing, provisioning, command, status notify |
| `webserver/` | no | **changed**: verify before dispatch; serve page only on the AP |
| `controller/`, `command/`, `actuator/`, `positioner/` | — | **unchanged** |

## Data model

NVS namespace `dock`:

| Key | Type | Notes |
| --- | --- | --- |
| `devkey` | 32 bytes | Generated by `esp_random()` on first boot. Never leaves the device except through the pairing window. |
| `nonce` | `uint64` | High-water mark of accepted nonces. Persisted lazily (see Risks). |
| `sta_ssid` | string | Up to 32 chars |
| `sta_pass` | string | Up to 64 chars |

BLE GATT service (128-bit custom UUIDs, generated at implementation time):

| Characteristic | Access | Payload |
| --- | --- | --- |
| Pairing | read | 32-byte device key — **only readable while the pairing window is open** |
| Provision | write | `nonce ‖ sig ‖ SSID\0password`; encrypted **and signed** |
| Command | write | `nonce ‖ sig ‖ one command byte`; encrypted **and signed** |
| Status | read / notify | the same JSON the HTTP status returns |

> Corrected during T16: an encrypted link is not authorisation. "Just works"
> pairing lets any device in range bond, so both writable characteristics carry
> an HMAC signature over the raw payload bytes, verified by
> `auth_verify_blob()`.

## Interfaces / APIs

```c
// auth/ -- no ESP-IDF headers, host testable
typedef void (*auth_hmac_fn)(const uint8_t key[32], const uint8_t *msg,
                             size_t len, uint8_t out[32]);

void   auth_init(auth_hmac_fn hmac);
size_t auth_canonical(char *out, size_t n,          // "POST\n/api/cmd\nc=e\n<nonce>"
                      const char *method, const char *path,
                      const char *query, uint64_t nonce);
bool   auth_nonce_acceptable(uint64_t nonce, uint64_t high_water);
bool   auth_verify(const uint8_t key[32], const char *method, const char *path,
                   const char *query, uint64_t nonce, const uint8_t sig[32],
                   uint64_t high_water);

// secrets/
esp_err_t secrets_init(void);                       // generates devkey on first boot
const uint8_t *secrets_device_key(void);
uint64_t  secrets_nonce_high_water(void);
void      secrets_note_nonce(uint64_t nonce);
esp_err_t secrets_set_wifi(const char *ssid, const char *pass);
bool      secrets_get_wifi(char *ssid, size_t n_ssid, char *pass, size_t n_pass);
void      secrets_rotate_key(void);                 // new key, unpairs every app

// session/ -- the dead-man, generalised across transports
typedef enum { LINK_HTTP, LINK_BLE, LINK_SERIAL } link_t;
void session_touch(link_t link);                    // call on every authorised message
void session_init(void);                            // arms the 2 s watchdog

// wifi_link/
void wifi_link_start(void);                         // APSTA + mDNS, falls back to AP
bool wifi_link_station_joined(void);

// ble_link/
void ble_link_start(void);
void ble_link_open_pairing(uint32_t seconds);       // serial 'P' or a button
bool ble_link_pairing_open(void);
```

HTTP requests gain two headers:

```
X-Dock-Nonce: 1734
X-Dock-Sig:   <base64 HMAC-SHA256 of the canonical string>
```

## Dependencies

- **NimBLE** (bundled with ESP-IDF; smaller than Bluedroid — use it, not Bluedroid)
- **mbedTLS** HMAC-SHA256 — already linked, no new dependency
- `mdns` component for `dock.local`
- A partition table with a larger app partition — **blocking, see Risks**

## Risks & tradeoffs

- ~~**Flash is the real risk.**~~ **Retired 2026-10-15.** The board has 16 MB
  (manufacturer 0x68, device 0x4018), not the 2 MB the build was configured for.
  The app partition is now 4 MB and the current build uses 20 % of it, leaving
  ~11 MB of flash unallocated for OTA slots or a data partition later. This was
  the single largest risk to the scope and it is gone.
- **Scope versus the semester.** BLE + Wi-Fi was the largest of the four options.
  The phasing below is the mitigation: stop after any phase and you still have a
  working, demonstrable dock.
- **BLE and Wi-Fi share one 2.4 GHz radio.** Coexistence works but costs
  throughput and adds latency jitter. The 2 s dead-man timeout must be measured
  with both active, not just one.
- **NVS wear from the nonce counter.** Writing every request would destroy the
  flash sector. Keep the counter in RAM, persist only every 256 increments, and
  on boot resume from the stored value plus 256 — losing a few nonces is free,
  reusing one is not.
- **The pairing window is a deliberate hole.** Anyone in range during it can
  take the key. Keep it short (60 s), require a physical or serial trigger, and
  log it loudly.
- **No RTC**, so replay protection cannot use wall-clock time — hence the
  monotonic counter rather than a timestamp.
- **Losing the browser UI as the primary interface.** It stays for service on the
  AP, but the demo story becomes "install the app", which is weaker for an
  assessor than "join the Wi-Fi and open a page". Worth stating in the report.

## Constitution check

| Rule | Status |
| --- | --- |
| Firmware authoritative | ✅ auth gate is in firmware; clients only propose |
| Dead-man on every transport | ✅ `session/` generalises it to BLE and HTTP |
| No delay / busy-wait | ✅ NimBLE is event-driven; watchdog is an `esp_timer` |
| Hardware-free logic is host tested | ✅ `auth/` has no IDF headers; HMAC injected |
| Secrets never in git | ✅ key generated at runtime into NVS; nothing tracked |
| `-Werror` on | ✅ unchanged |
| **Flash budget** | ✅ **resolved.** 16 MB verified, 4 MB app partition, 80 % free. No longer a constraint on this feature. |

## Phasing

| Phase | Delivers | Demo at the end |
| --- | --- | --- |
| 0 | Flash audit, partition table | ✅ **done** — 16 MB verified, 4 MB app partition, 80 % free |
| 1 | `auth` + `secrets` + signed HTTP on the existing AP | `curl` is refused; signed request works |
| 2 | `wifi_link` station + fallback + mDNS | Dock joins your hotspot; phone keeps cellular |
| 3 | `ble_link` pairing + provisioning | Provision Wi-Fi over BLE from the app |
| 4 | BLE command + status characteristics | Control with Wi-Fi switched off entirely |
| 5 | KMP `DockClient` over both links | One app, both transports |
